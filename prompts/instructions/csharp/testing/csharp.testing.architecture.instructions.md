## C#

### Architecture/Fitness Tests
- Fitness and architecture tests MUST live in a project named `<RootNamespace>.ArchitectureTests`.
- Fitness and architecture tests MUST use NUnit; compiled dependency rules MUST use ArchUnit.NET, and source-file convention rules MUST use Roslyn syntax analysis.
- Architecture/Fitness tests MUST NEVER be modified by the agent, even if they are failing, unless the user EXPLICITLY asks for it.
- Architecture tests MUST explicitly load all relevant production assemblies, exclude test assemblies, and reuse the loaded architecture for the test run.
- Every rule MUST select expected types; tests MUST fail when a selector matches none rather than pass vacuously.
- Tests MUST enforce the documented layer dependency matrix. Domain MUST NOT depend on Application, Infrastructure, or API; Application MUST NOT depend on Infrastructure or API; Infrastructure MUST NOT depend on API; and API MUST NOT reference Domain directly.
- Dependency rules MUST be checked independently at both levels: type dependencies in the loaded production assemblies and project/assembly references declared by the production projects. A passing type-dependency check MUST NOT substitute for the project/assembly-reference check.
- API boundary rules MUST verify that API code does not directly depend on Entity Framework, DynamoDB, or their persistence namespaces. API MUST NOT contain public repositories or command/query handlers; controllers, request/response contracts, and validation contracts MUST use the prescribed API namespaces; and controllers MUST NOT depend on repositories.
- Application boundary and placement rules MUST verify that Application does not depend on persistence implementations, DynamoDB, or Entity Framework, and does not expose controllers or middleware. Repository and service interfaces, commands, queries, and their handlers MUST be placed in their designated namespaces. Validators MUST be placed in the matching command or query use-case namespace.
- Domain boundary rules MUST verify that Domain does not depend on ASP.NET Core, Entity Framework, DynamoDB, Dapper, or MediatR. Domain types MUST NOT use persistence attributes. Public controllers, handlers, DTOs, validation contracts, commands, queries, and repositories MUST be prohibited in Domain.
- Architecture tests MUST verify that production code projects do not declare `InternalsVisibleTo`.
- Tests MUST check cycles where components are defined as independent or acyclic. Do not assume layer names or impose a layered design beyond the documented matrix. Any permitted cycle MUST be documented and narrowly scoped.
- Source-file convention tests MUST live separately from dependency tests in a `SourceFileConventionTests` fixture within the architecture test project.
- Source-file tests MUST enforce exactly one declared type per handwritten `.cs` file and an exact, case-sensitive match between its filename stem and type identifier. Count classes, interfaces, structs, records, enums, and delegates, including nested declarations; compare generic types by identifier without arity.
- Source-file tests MUST explicitly define the checked projects, exclude generated files and `bin`/`obj`, and fail when no eligible files are found or required sources are unavailable in CI. Failures MUST identify the file and violated convention.
- Nested types, partial declarations, and files containing only top-level statements MUST NOT receive implicit exemptions. Any necessary exception MUST be documented and narrowly scoped; partial declarations MUST NOT bypass filename matching.
- Enforce applicable C# instruction conventions as well as the documented architecture. Reuse configured analyser results for equivalent checks rather than implementing duplicate analysers; architecture tests MUST verify that required analyser checks are enabled and enforced.
- Failure messages MUST identify the violated boundary and reason. Rule exceptions MUST be explicit and narrowly scoped.
- Architecture tests are exempt from the business-unit-test assertion requirement.

### Enforcement Scope And Mechanisms
- Every mechanically decidable requirement in the linked instruction sources below MUST have a corresponding fitness check, including source formatting rules. Preserve each source's applicability, preferences, exceptions, thresholds, and framework-specific conditions; do not turn contextual preferences into unconditional prohibitions.
- Use ArchUnit.NET for compiled type dependencies, Roslyn syntax and semantic analysis for declarations, bodies, symbols, and trivia, and project/solution parsing plus evaluated MSBuild metadata for configuration and references. Resolve symbols and overloads rather than matching names or source text alone; formatting checks MAY inspect Roslyn source text and trivia.
- Keep source conventions in `SourceFileConventionTests`; place project/solution and test-source checks in separate fixtures. Explicitly include relevant handwritten production and test sources for convention checks, while keeping test assemblies excluded from production dependency rules. Resolve partial types across files and inspect inactive preprocessor branches where the convention applies to all source text.
- Scope conditional checks using explicit project metadata, documented roles, package references, and supported configurations. Fail on missing required inputs or unexpectedly empty selectors; explicitly mark genuinely inapplicable rules with a reason rather than inventing applicability. Conflicting source instructions MUST be reported for resolution, not silently reconciled or enforced as mutually impossible rules.
- Runtime correctness, security guarantees, business meaning, exhaustive scenario coverage, documentation accuracy, historical user intent, and agent workflow cannot be proved by static architecture checks alone. Enforce their identifiable structural prerequisites and known forbidden patterns, and require the appropriate behavioural tests or review for the remaining claims; never present a heuristic as proof.

### Core Source Conventions
- Enforce [coding conventions](../csharp.coding.instructions.md): explicit types; no ternaries, tuples, `ref`, optional parameters, regions, or `#nullable enable`; explicit namespace/type blocks and `static void Main`; allowed partial-class exceptions; explicit accessibility; member-kind and accessibility ordering; field ordering; and the seven-parameter limit for methods, constructors, and lambdas.
- Check statically decidable coding forms: compound increment/decrement assignments, default initialisation followed by an overriding `if`, preferred equality calls and nullable guards, static methods without instance state, constant-property form, braced control-flow bodies, overload adjacency and parameter-count ordering, matching interface/implementation parameter names, target-typed construction, expression-bodied single-statement methods and computed properties, auto-properties for models/entities/contracts/settings, and no `init` accessors. Retain contextual exceptions and do not infer semantic simplicity from parameter count alone.
- Check eligible classes for sealing, `public sealed` model/entity/settings declarations, equivalent colocated interfaces for non-static classes with public methods, and complete public interface contracts. Respect documented inheritance, model/entity, framework, and enumeration-class exceptions. Check primary constructors and direct parameter use in services/controllers/startup classes; require explicit justification for conditional async, cancellation-token, custom-exception, and concrete-versus-interface choices rather than banning required uses.
- Check the coding source's analyser-prevention rules: Cognitive Complexity at most 15 using the configured metric, no nested conditional expressions, reusable serializer options, `GeneratedRegex` for constant patterns with permitted partial declarations, reused regexes and non-mutated repeated array arguments, non-redundant field initialisers, named repeated protocol literals, and accessible custom exceptions. Use data-flow analysis where necessary; do not claim that matching allocation syntax proves hot-path behaviour or mutation safety.
- Enforce [indentation and line-splitting conventions](../csharp.indentation.instructions.md), including the 72-character conditional and 96-character argument/signature thresholds, four-space continuations, operator placement, accessor/property layout, expression-body and initialiser layout. Also enforce the coding source's brace placement, `else if` layout, method spacing, control-flow spacing, and prohibition of blank lines before closing delimiters.
- Enforce [namespace and using conventions](../csharp.namespaces.instructions.md): block namespaces, namespace/folder correspondence, prescribed role namespaces, no `.Interfaces` namespaces, colocated interfaces, external using directives, no inline fully qualified types, grouped/alphabetised imports, and exactly one blank line before the namespace. Determine responsibility and layer/domain placement from documented project roles rather than guessing from names.
- Enforce [naming conventions](../csharp.naming.instructions.md): built-in aliases, uppercase public/protected identifiers, PascalCase classes/methods, camelCase private fields without underscore prefixes, permitted boolean forms, and role-specific data-object, domain-model, request, response, and settings names. Validate grammatical or contextual naming through explicit role/name mappings where syntax alone is insufficient.
- Enforce [interface conventions](../csharp.interfaces.instructions.md): `I`-prefixed PascalCase, eligible class/interface pairing, implementation alignment, and XML summaries on NuGet interface members. For public NuGet classes/members, including enum members, check XML-summary presence; use a versioned public-API baseline to detect removals and require explicit approval. Documentation freshness and approval history require review evidence.

### Specialised Type And API Conventions
- Enforce [collection conventions](../csharp.collections.instructions.md): `IEnumerable<T>` collection parameters/returns, the XML-serialised entity/data-object `List<T>` property exception, and C# 12 collection-expression initialisation where supported. Check identifiable in-memory query patterns against the LINQ preference without treating all loops as queries.
- Enforce [controller conventions](../csharp.controllers.instructions.md): plural-noun controller naming using explicit pluralisation mappings where needed, non-generic `ActionResult` action returns, and expression-bodied single-expression `ProcessRequest(...)` delegates. Enforce explicit input-binding attributes and prohibit direct request-value reads under the coding instructions.
- Enforce [mapping conventions](../csharp.mapping.instructions.md): dedicated identically named `*MappingExtensions` files/classes, `.Mappings` namespaces, `internal static` classes/methods, extension receivers, prescribed singular/plural conversion names and directions, no mapping methods in implementation classes, and required expression-bodied initialisers without temporary-return locals.
- Enforce [enumeration conventions](../csharp.enumerations.instructions.md): no `.Enumerations`/`.Enums` namespaces, domain colocation, and enumeration-class use when documented data/string-serialisation/equality requirements demand it. Check public visibility, private constructors, private static readonly dictionaries, `nameof` keys/constructor arguments, expression-bodied value properties, `IEquatable<T>`, equality/hash overrides, equality operators, `FromString`, `GetValues`, and implicit string conversion. Verify safe-default control-flow structure where statically determinable; use behavioural tests for fallback safety, registered-value completeness, and equality consistency.
- Enforce [null, exception, and casting conventions](../csharp.error-handling.instructions.md): null patterns instead of equality comparisons, no `??` while preserving permitted `??=`, and bare rethrows rather than rethrowing the caught exception. Check BCL-exception preference and unsafe-cast patterns only where applicability is established by type/flow analysis or documented exceptions.
- Enforce [custom-exception conventions](../csharp.exceptions.instructions.md): `Exception` suffix, matching inner-exception overloads for each constructor, and constructor chains ultimately forwarding appropriate arguments to the base exception constructor.
- Enforce [serialisation conventions](../csharp.serialisation.instructions.md): required date/time format-provider or format overloads, `JsonPropertyName` mappings that replace API DTO property-name segments `Identifier` with `id`, and cached/reused static readonly `JsonSerializerOptions` instead of repeated allocations in loops or identified hot paths.
- Enforce [logging conventions](../csharp.logging.instructions.md): an `Operation` on every NuciLog call, structured `LogInfoKey` values where identifiable, dedicated exception arguments instead of message/stack-trace text, custom logging types in `[Project].Logging`, and sensitive-key constructors passing `true` to the protected base constructor. Respect the documented free-text exception rather than banning every `Message` value.
- Enforce statically traceable [security requirements](../csharp.security.instructions.md): reject known sensitive sources flowing unmasked into logs, exception messages, telemetry, or NuciLog message/operation/status/key names; require sensitive structured keys for secret values. Use semantic/data-flow checks with an explicit source/sink/masking catalogue; require security tests/review for unresolved flows rather than asserting complete leakage prevention.
- Enforce applicable [NuGet/network usage rules](../csharp.nuget.usage.instructions.md) in verified hmlendea-owned repositories: `NuciWeb.HTTP` dependency, `HttpClientCreator` creation paths, prescribed `UserAgentFetcher`/`NetworkUtils` calls, and `IPAddress.IPv6Any` for listeners documented to accept IPv6 unless explicitly exempted. Package-documentation lookup, version verification, and avoiding investigative decompilation remain agent-workflow requirements, not source architecture assertions.
- Enforce applicable [MonoGame/NuciXNA conventions](../csharp.monogame.instructions.md): `GuiImage` instead of raw texture storage/direct loading, `GuiText` instead of raw font/text-rendering APIs, no direct `GuiControl` lifecycle calls, correct child versus screen registration APIs, and `Point2D.Empty`/`Size2D.Zero`. Check named artwork-measurement constants, proportional use, and runtime image dimensions in identified layout code; actual artwork measurements and visual correctness require external evidence.

### Project And Solution Conventions
- Enforce [project conventions](../csharp.csproj.instructions.md): .NET 10.0 minimum across target frameworks/configurations, alphabetically ordered package references, disabled implicit usings, latest language version, enabled nullable references, and `IsPackable` matching documented NuGet publishing intent. Inspect declared values and evaluated metadata, including imported/conditional properties; report contradictory or missing required declarations.
- Enforce [solution conventions](../csharp.slnx.instructions.md): `.slnx` preference, prescribed SDK-style `<Solution>` structure without XML declaration/version/root attributes, `Project` elements with only `Path`, sibling project folders named after their projects without a `src` nesting layer, main/source/test ordering, unit-project naming, and explicit `IsTestProject`/`ExcludeFromCodeCoverage` flags on every test project.

### Test Source Conventions
- Enforce [shared testing conventions](csharp.testing.instructions.md): subject-based `Tests` class names, parameter limits, NUnit fixture/test attributes where that framework applies, method grouping without comment banners, bottom-placed private static `BuildXxx` helpers, static state-free helpers, top-level internal dummy implementations in separate files, and cached serializer options. Detect known platform-specific paths/APIs/culture-dependent operations; portability and comprehensive branch/scenario coverage still require appropriate execution and review.
- Enforce [unit-testing conventions](csharp.testing.unit.instructions.md): `Given..._When..._Then...` names, permitted/default NUnit 4.x and Moq framework selection, no unapproved xunit adoption, at least two cases when parameterised, no reflection directly testing non-public code, prescribed NUnit constraint/assertion forms, expression-bodied single-assert tests without Arrange/Act, multiline assertion formatting, `[SetUp] SetUp()` mock/SUT construction and private fields, and an assertion, Moq verification, or `ExpectedResult` in every business unit test. Resolve delegated helpers before declaring a test assertion-free; check identifiable configuration-only tests and leave grammatical naming/practical parameterisation decisions to explicit mappings or review.
- Enforce [integration-testing conventions](csharp.testing.integration.instructions.md): dedicated correctly named integration projects, no integration tests in production/unit projects, permitted/default framework dependencies, no unapproved xunit adoption, response-body and status assertions, framework-compatible parameterisation, and identifiable mocked external dependencies. Use explicit test metadata to classify integration/configuration tests; static structure alone cannot prove complete HTTP-scenario coverage or deterministic execution.
- Enforce this file's own mechanically checkable requirements: architecture-project naming, NUnit/ArchUnit.NET/Roslyn usage, explicit production-assembly inventories and reuse, separate convention fixtures, source availability/exclusions, non-vacuous selection safeguards, and explicit scoped rule exceptions. Protection against unrequested edits is an agent-workflow requirement, not a runtime assertion; this enforcement instruction does not authorise modifying protected tests without an explicit user request.
